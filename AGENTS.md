# AGENTS.md

Guidance for coding agents working in this repository. Keep it up to date whenever the
architecture, build commands, or conventions change.

## What this is

An Android app that remembers where you parked: it watches the Bluetooth connection to a
paired car and, on disconnection, saves the current GPS position. The user can then see the
spot on a map, get driving directions, browse the parking history, and share the location.
Everything is local (Room + DataStore); there are no accounts and no backend.

The official project name is **AutoSpot**, used consistently for the Gradle root project, the XML
themes and the user-facing label. The Android package keeps its own spelling:

| Thing | Value |
|---|---|
| Repository | `github.com/dicren/autoSpot` |
| Gradle root project | `AutoSpot` |
| Android package / `applicationId` | `com.dicren.autospot` |
| App label shown to users | `AutoSpot` |
| XML theme names | `Theme.AutoSpot`, `Theme.AutoSpot.Dialog` |

`com.dicren.autospot` is the published `applicationId`: never rename it, since that would create
a different app on the Play Store and orphan existing installs.

## Tech stack

- **Language:** Kotlin 2.4.21 (AGP 9 built-in Kotlin), JVM target 17
- **UI:** Jetpack Compose, Material 3, `material-icons-extended`; Compose BOM `2026.11.01`
- **Maps:** Google Maps SDK + `maps-compose` 9.0.1
- **Location:** `play-services-location` 21.4.0 (FusedLocationProviderClient)
- **Persistence:** Room 3.0.3 (KSP, `androidx.room3`) + DataStore Preferences 1.3.0
- **Build:** Gradle 9.9.2 wrapper, AGP 9.5.2, KSP 2.3.14, `compileSdk` 37.1
- **Performance:** startup baseline profile generated by the `:baselineprofile` module
- **SDK:** `compileSdk` 37.1, `targetSdk` 37, `minSdk` 31 (Android 12)
- **DI / architecture:** manual DI (`AutoSpotApp` + `di/AppContainer`), one ViewModel per
  screen (`ParkingViewModel` + `StateFlow<ParkingUiState>`) and plain repositories. No Hilt, no
  Koin, no navigation library.

AGP 9 compiles Kotlin itself: **never apply `org.jetbrains.kotlin.android`**. The Compose compiler
plugin (`org.jetbrains.kotlin.plugin.compose`) is still required and its version must match
Kotlin. The root `build.gradle.kts` pins KGP/KSP through `buildscript` classpath because AGP
otherwise ships older versions.

Dependencies are declared in the version catalog `gradle/libs.versions.toml`. Add new libraries
there, not inline in `app/build.gradle.kts`.

Formatting is enforced by **ktlint through Spotless** (`.editorconfig` holds the settings; the
`function-naming` and `class-naming` rules are disabled because test names are backticked
sentences). CI runs on GitHub Actions: `.github/workflows/ci.yml` runs `spotlessCheck`,
`testDebugUnitTest`, `lintDebug`, `lintVitalRelease`, `assembleDebug`, `assembleRelease` and
`bundleRelease`, then fails if KSP regenerated a Room schema that is not committed. The
configuration cache is enabled in `gradle.properties` and reused by every CI invocation.

Release builds enable R8 and resource shrinking. `proguard-rules.pro` deliberately holds only
project-specific rules: Room, Play Services, Maps, DataStore and coroutines ship their own
consumer rules. Blanket `-keep` rules for those packages inflate the APK and disable
optimizations. Verify any R8 change with a release APK on a device, not just `assembleRelease`.

## Commands

Run from the repo root:

```bash
./gradlew assembleDebug          # build the debug APK
./gradlew compileDebugKotlin     # fast type-check
./gradlew installDebug           # install on a connected device/emulator
./gradlew assembleRelease        # release APK (minified; signed if keystore.properties exists)
./gradlew bundleRelease          # release AAB (signed if keystore.properties exists)
./gradlew lintDebug              # Android Lint
./gradlew lintVitalRelease       # release-only fatal lint checks
./gradlew testDebugUnitTest      # unit + Robolectric + Compose tests
./gradlew spotlessApply          # format Kotlin with ktlint
./gradlew :app:generateBaselineProfile  # regenerate the startup profile (device, API 33+)
./gradlew connectedAndroidTest   # launcher smoke test (device required)
```

Use JDK 17 or newer (JBR 21 is installed on this machine). The Android SDK path comes from
`local.properties`, which is gitignored — never edit or commit it.

### Baseline profiles

The `:baselineprofile` module (`com.android.test` + `androidx.baselineprofile`) generates the
startup profile on a connected device or emulator (API 33+, no root needed):

```bash
./gradlew :app:generateBaselineProfile
```

**Never run this on a phone with real app data:** it installs the non-minified release build and
a test APK, then uninstalls both when the connected test finishes, which wipes the app data. Use a
dedicated emulator.

The generator test sets `includeInStartupProfile = true` and grants
`ACCESS_BACKGROUND_LOCATION` as well, so the parking screen is profiled without the permission
banner and the rationale dialog in the way. The plugin writes
`app/src/release/generated/baselineProfiles/{baseline-prof.txt,startup-prof.txt}`, which are
committed; debug builds ignore them. **The two files are not duplicates of each other:** AGP
compiles the first into `assets/dexopt/baseline.prof` and the second into
`assets/dexopt/baseline.profm` (the startup profile), so both must stay committed even when the
text is identical. With a single test that sets `includeInStartupProfile`, identical text is the
expected result; do not "clean up" one of them.

**Regenerate and commit the profile in the same change whenever startup-critical code changes**
(the activity/application entry points, `AutoSpotApp`/`AppContainer`, the first Compose screen,
the Room builder or the DataStore read). A stale profile does not break anything — ART ignores
rules for code that no longer exists and AGP filters them — it just stops helping the new code.
CI cannot check this because it has no device, so it is on the person making the change.

### Google Maps API key

`app/build.gradle.kts` reads `MAPS_API_KEY` from `local.properties` (falling back to
`local.defaults.properties`) and injects it as the `MAPS_API_KEY` manifest placeholder, which the
manifest uses for `com.google.android.geo.API_KEY`:

- Real key: `MAPS_API_KEY=...` in `local.properties` (gitignored).
- Fallback: `local.defaults.properties` contains `MAPS_API_KEY=YOUR_API_KEY_HERE`, so the build
  succeeds without a key but the map stays blank and the Maps SDK logs an authorization failure.

The old secrets Gradle plugin was removed: it did not populate the unit-test manifest under AGP 9.

### Release signing

Copy `keystore.properties.example` to `keystore.properties` (both at the repo root; the real file
is gitignored) and fill in `storeFile`, `storePassword`, `keyAlias` and `keyPassword`. When that
file exists, `app/build.gradle.kts` registers a `release` signing config and release builds are
signed automatically. Without it, release builds are unsigned — only debug builds work.
`storeFile` is resolved relative to the repo root by default (`autospot-release.keystore`).

## Runtime architecture

### Entry points

- **`MainActivity`** — launcher. Asks for `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION` and
  `BLUETOOTH_CONNECT` (API 31+) only once the onboarding flag is true, so the first system dialog
  does not appear before the intro. `rememberSaveable` keeps a denial from re-prompting on
  rotation; a later cold start asks again if a permission is still missing. It deliberately does
  **not** request `ACCESS_BACKGROUND_LOCATION`: on Android 11+ that request sends the user to a
  system settings page, so `ParkingScreen` explains the "Allow all the time" requirement first
  (once, persisted in DataStore, and only when a vehicle exists) and only then launches it. The
  onboarding flag is collected as `Boolean?`: `null` (not read yet) shows an empty themed surface
  instead of flashing the map before onboarding.
- **`NavigateActivity`** — headless (`Theme.AutoSpot.Translucent`, `excludeFromRecents`) target of
  the "Navigate to my car" shortcuts. Reads an optional `vehicle_id` extra, falls back to the
  active vehicle, queries Room from a `lifecycleScope` coroutine, and fires
  `google.navigation:q=<lat>,<lon>&mode=w` pinned to `com.google.android.apps.maps`. Shows a toast
  and finishes if Maps is missing, there is no saved location, or the storage read fails; the
  failure path must never crash a headless shortcut. **Never use `Theme.NoDisplay` here**: the
  activity suspends before finishing, and Android throws "did not call finish() prior to
  onResume() completing" (see trap 10).
- **`CreateShortcutActivity`** — handles `android.intent.action.CREATE_SHORTCUT` (launcher's
  "add to home screen"). Shows a vehicle picker and returns a pinned
  `ShortcutInfoCompat` (`navigate_to_<vehicleId>`) pointing at `NavigateActivity`.

### Services

- **`BluetoothMonitorService`** — sticky foreground service
  (`foregroundServiceType="connectedDevice"`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`) that
  registers a runtime receiver for `ACTION_ACL_CONNECTED/DISCONNECTED`,
  `BluetoothA2dp`/`BluetoothHeadset` connection-state changes, and adapter state changes.
  `bluetooth/BluetoothIntents` reduces the broadcast to a `BluetoothEvent`; the service then looks
  the MAC up in Room and, if it belongs to a vehicle, starts `LocationSaveService` with that id.
  Events pass through `DisconnectionDebouncer` (10 s per vehicle, `Mutex` + injected clock), so
  there is no concurrent access to shared state. It calls `stopSelf()` when
  `Permissions.canMonitor` is false at start **and again before every disconnection**, because
  permissions can be revoked while it runs; in the second case it posts the "auto-save is
  disabled" notification, since nothing was being saved. It catches `Exception` from
  `startForeground` and posts the same notification instead of losing the save silently; the
  parking screen shows a snackbar when the service cannot even be started. Its
  notification is built by `AppNotifications` (`bluetooth_monitor_channel_v2`, `IMPORTANCE_MIN`,
  monochrome `ic_notification`, dismissible). The old `bluetooth_monitor_channel` is deleted when
  the channels are created because Android ignores importance changes on an existing channel.
- **`LocationSaveService`** — one-shot foreground service. Enters the foreground first and stops
  with the failure notification when the location permission is gone (trap 13), then runs
  `SaveParkingLocation`: a fresh high-accuracy fix bounded by a 15 s
  timeout, falling back to `lastLocation` only if it is younger than 5 minutes and, like the fresh
  fix, its reported accuracy is at most 100 m. The two sources are asked independently: an
  exception from the fresh fix (Play Services unavailable) still tries the last known one. Saves
  are serialised with a `Mutex` and each start stops with `stopSelfResult(startId)` in a `finally`,
  so even an unexpected failure cannot leave the foreground notification alive. A failed save
  posts a notification instead of failing silently.
- **`BootReceiver`** — on `BOOT_COMPLETED` **and** `MY_PACKAGE_REPLACED` (the process is killed by
  an app update), restarts `BluetoothMonitorService` only if at least one vehicle is stored
  **and** `Permissions.canMonitor` is true. The receiver is not exported: both actions are system
  broadcasts. It logs `ForegroundServiceStartNotAllowedException`
  explicitly: Android 12+ may refuse the start, and the monitor then starts the next time the app
  is opened.

`ParkingScreen` starts `BluetoothMonitorService` only when the vehicle list is non-empty and every
required permission is granted, and stops it when the last vehicle is removed. It waits for
`ParkingUiState.isReady` (the first real repository emission) before doing either: acting on the
default state would stop the monitor that `BootReceiver` had just started. When monitoring starts
and `POST_NOTIFICATIONS` is missing (Android 13+), the screen asks for it; denying it only hides
the ongoing notification, the service keeps running. The "Allow all the time" rationale is only
shown after precise location is granted and a vehicle exists, hides the permission banner while
the dialog is on screen, and is recorded in DataStore only when the user confirms or dismisses it.
A dialog that never reached the user is shown again; "Not now" is persisted so it does not nag.

### UI

All UI is Compose, split in `ui/`:

- `ui/parking/ParkingScreen.kt` — layout and state orchestration: map, overlays, cards, snackbar
  and sheets. It reads `ParkingViewModel.uiState`, sends user actions to the ViewModel, and
  keeps the relative "parked at" text fresh with a one-minute ticker (`rememberNow`).
- `ui/parking/ParkingMessages.kt` — maps each one-shot `ParkingEvent` to its localized snackbar
  text, kept out of the screen.
- `ui/parking/ParkingEffects.kt` — the side effects: refresh on resume, start/stop the monitor,
  request `POST_NOTIFICATIONS`, explain the background-location requirement and follow the
  displayed spot with the camera.
- `ui/parking/ParkingControls.kt` — the top banners/vehicle card, compass FAB and navigate FAB.
- `ui/parking/ParkingMap.kt` — the `GoogleMap` + marker, kept out of the orchestrator.
- `ui/parking/ParkingSheets.kt` — the vehicle list, history and "clear all" dialogs, with a
  `ParkingSheetCallbacks` data class so the composable does not take twenty lambdas.
- `ui/parking/ParkingViewModel.kt` + `ParkingUiState.kt` — `StateFlow<ParkingUiState>` built from
  the repositories (`combine` + `flatMapLatest`), one-shot `ParkingEvent`s for snackbars, and the
  action methods. Repository writes are wrapped so a storage failure emits
  `ParkingEvent.OperationFailed` instead of crashing the app. Switching the active vehicle clears
  the selected history item, and the location list is filtered by the active vehicle id so the
  previous car's history cannot appear for a frame while the new Room flow emits. `isReady` stays
  false until the first real emission so the UI never acts on the defaults.
- `ui/parking/components/` — stateless components (`VehicleCard`, `Banners`, `LocationCard`,
  `NoLocationCard`, `HistorySheet`, `VehiclesSheet`, `VehicleEditDialog`,
  `BackgroundLocationDialog`) that take state and callbacks, which is what the Compose tests
  render. `Previews.kt` holds the design-time previews.
  The edit dialog receives the paired-device list instead of reading the adapter, so it can be
  tested without Bluetooth; only `ParkingScreen` touches `BluetoothDevices.paired`.
- `ui/format/ParkingTimeFormatter.kt` — relative time with an injected `now` and a locale-aware
  absolute fallback.
- `OnboardingScreen.kt` — `HorizontalPager` intro; the final page writes the DataStore flag.
- `ui/theme/` — Material 3 color scheme, typography, `AutoSpotTheme`. The window themes have a
  `values-night` variant so the startup/splash background follows the system dark mode.

The map is edge-to-edge; the cards apply `WindowInsets.safeDrawing` themselves.

### Data layer

- **`AppDatabase`** — Room **3** (`androidx.room3`), version **4**, database name
  `parking_database`, singleton via `getDatabase(context)`, `exportSchema = true`. Schemas are
  generated into `app/schemas/` (KSP `room.schemaLocation`) and committed. The builder sets
  `BundledSQLiteDriver()` on devices (same SQLite build everywhere); migrations are `suspend` and
  use `SQLiteConnection` + `androidx.sqlite.async.executeSQL`. `MIGRATION_3_4` adds the unique
  Bluetooth index and repairs duplicates;
  `fallbackToDestructiveMigrationFrom(dropAllTables = true, 1, 2)` covers the unknown legacy
  schemas only. From v3 onward every version bump must ship an explicit `Migration`, or the app
  crashes on upgrade. The Room 3 package and the Room 2 one are different: never mix them.
- **`VehicleEntity`** — `vehicles` table: name, Bluetooth MAC address (**unique index**), Bluetooth
  display name, and a single `isActive` flag. Room cannot express a partial unique index for the
  active flag, so `VehicleDao` keeps the invariant with `@Transaction` methods.
- **`ParkingLocationEntity`** — `parking_locations` table, foreign key on `vehicleId` with
  `CASCADE` delete and an index on `vehicleId`.
- **DAOs** expose `Flow` queries for UI plus `...Once` `suspend` variants for services.
  `activateOnly`, `insertVehicleAndActivate`, `deleteVehicleAndKeepOneActive` and
  `insertAndPrune` are transactional. Parking history orders by `timestamp DESC, id DESC` so
  entries saved in the same millisecond still have a stable newest one.
- **Repositories** (`VehicleRepository`, `ParkingRepository`, `SettingsRepository`) and the
  shared `SaveParkingLocation` use case are built by `di/AppContainer`; services and the ViewModel
  must take the use case from there instead of constructing their own. The container also exposes
  `ioDispatcher`, which the services and `BootReceiver` use for their scopes, so tests can replace
  it with a deterministic dispatcher. `SaveParkingLocationUseCase`
  is total: every non-cancellation failure becomes `SaveResult.Error` instead of escaping to a
  service or view-model coroutine. `addVehicle` uses
  `INSERT OR IGNORE` on the unique Bluetooth address and returns `Added`/`Duplicate` without
  depending on a driver-specific exception; deleting the active vehicle activates another; the
  history is capped at 100 rows per vehicle.
- **`SettingsRepository`** wraps the `settings` DataStore. It treats an `IOException` (corrupt
  file) as "not onboarded" instead of crashing, and persists the onboarding flag plus the fact
  that the background-location rationale was shown and acted on. Writes are best effort: a failed
  write must not crash the app.
- Cloud backup / device transfer rules (`res/xml/backup_rules.xml`,
  `res/xml/data_extraction_rules.xml`) include the three database files and the DataStore
  preferences (`datastore/settings.preferences_pb`) in **both** `<cloud-backup>` and
  `<device-transfer>`. Android copies the backup to the user's own Google account, encrypted by
  the platform; AutoSpot never receives or has access to it. Keep both XML files and the privacy
  policy in sync; the policy must not claim that data is excluded from cloud backup.

## Conventions

- **Strings:** every user-visible string lives in `res/values/strings.xml` and is read with
  `stringResource` / `getString`. Nine locales exist (`values`, `de`, `es`, `fr`, `it`, `ja`,
  `ko`, `ru`, `zh`) and all currently carry the same 85 strings plus 2 plurals (87 entries).
  When adding or changing a string, update **all nine** files; missing translations silently fall
  back to English. `LocaleResourcesTest` fails CI when the key sets differ or a translation
  changes the `%s`/`%d` arguments of a string or plural. Spanish, French and Italian need a
  `quantity="many"` item in plurals or lint fails.
- **Permissions:** check runtime grants through `util/Permissions`, not raw
  `checkSelfPermission`. `Permissions.locationAccuracy` distinguishes `NONE` / `COARSE` /
  `PRECISE`: only precise is useful for a parking spot, and the banner names approximate access as
  the cause. Services must stop (`stopSelf`) instead of starting a location-typed foreground
  service without permission. Reading `bondedDevices` must be wrapped: it throws
  `SecurityException` without `BLUETOOTH_CONNECT` (done in `util/BluetoothDevices`).
- **Tests:** Robolectric tests that need a container use the shared doubles in
  `app/src/test/java/com/dicren/autospot/util/TestDoubles.kt`. `FakeParkingRepository` suspends on
  purpose so headless activities are tested with a real suspension.
- **Code identifiers, comments and KDoc:** English. Committed docs: English.
- **State:** screens collect a `StateFlow<UiState>` from their ViewModel with
  `collectAsStateWithLifecycle`; ViewModels never hold `Context` (the factory captures the
  application context) and expose actions as methods. Keep one-shot messages in a `SharedFlow`.
  A collector that lives as long as the screen (one keyed on the ViewModel) must read translated
  strings through `rememberUpdatedState`: the ViewModel survives a configuration change, so a
  per-app language switch would otherwise leave it showing the previous locale.
- **Coroutines:** ViewModels own UI work through `viewModelScope`; services own a
  `CoroutineScope(SupervisorJob() + Dispatchers.IO)` and cancel it in `onDestroy`. Do not create
  ad-hoc `CoroutineScope`s for database writes. `rememberCoroutineScope` is only for animations.
- **Versioning:** bump `versionCode` / `versionName` in `app/build.gradle.kts` (`2` / `1.1`
  today) before a store release. Release builds are minified by R8.
- **Branding assets** live at the repo root: `logo.png`, `logo512.png`, `logo.xcf`,
  `claim.png`, `claim.xcf`, plus `app/src/main/ic_launcher-playstore.png`.

## Known issues and traps

Traps and limitations verified in the current tree. Fix them deliberately, not as a side effect.

1. **The Bluetooth receiver must stay `RECEIVER_EXPORTED`.** The Bluetooth stack is a separate
   system app, not the system UID, so a `RECEIVER_NOT_EXPORTED` receiver never sees
   `ACL_CONNECTED/DISCONNECTED` and the app silently stops saving locations. Verified on Android
   16. These actions are protected broadcasts, so other apps cannot spoof them.
2. **Static shortcut is package-bound:** `res/xml/shortcuts.xml` hardcodes
   `com.dicren.autospot.NavigateActivity`. If the Android package ever changes, update it there
   too; dynamic shortcuts built by `CreateShortcutActivity` follow the code automatically.
3. **Release builds need `keystore.properties`:** without it they come out unsigned and the store
   rejects them. `autospot-release.keystore` lives at the repo root and is gitignored; never commit
   it or its passwords.
4. **`BundledSQLiteDriver` does not throw `SQLiteConstraintException`.** The production driver
   surfaces constraint failures as `android.database.SQLException` (its native libraries reference
   that class), so catching `SQLiteConstraintException` only works in tests, which use
   `AndroidSQLiteDriver`. Use `OnConflictStrategy.IGNORE` and check the returned row id (or catch
   `android.database.SQLException`) for anything that depends on a unique index. The failure type
   was confirmed in the bundled driver's native libraries; the release APK builds and runs with
   the `IGNORE` strategy.
5. **targetSdk is 37 (Android 17).** The Android 17 targeting changes (widget memory caps,
   MessageQueue internals, static-final reflection, local-network permission, SMS OTP, audio,
   orientation on large screens) do not apply to this app. Verified on an API 37 emulator:
   map, monitor, bottom sheets, navigation to Maps and landscape.
6. **Migration schemas are test assets:** `app/build.gradle.kts` adds `app/schemas` to the **debug**
   assets so `MigrationTestHelper` can read them under Robolectric. They never ship in release.
   Every schema bump must keep the exported JSON committed, or `MigrationTest` fails; CI runs
   `git diff --exit-code -- app/schemas` after KSP to catch it.
   Unit tests use `AndroidSQLiteDriver`, not the bundled one: `BundledSQLiteDriver` needs the
   `sqliteJni` native library, which is not available on the JVM test host.
7. **No Bluetooth on the emulator:** the app is only meaningfully testable on a physical device
   with a paired car. Use `adb logcat -s BluetoothMonitorService LocationSaveService BootReceiver`
   to follow the flow. You can also simulate a disconnection by adding a connected device (watch,
   earbuds) as a vehicle and turning Bluetooth off with `adb shell cmd bluetooth_manager disable`.
   To exercise Room and Maps on an emulator, install the debug APK, seed
   `databases/parking_database` through `run-as`, then reinstall the debug-signed release APK over
   it: both are signed with the same key, so `-r` keeps the data.
8. **Maps needs `org.apache.http.legacy` on old Play Services.** The manifest declares
   `<uses-library android:name="org.apache.http.legacy" android:required="false" />`. Without it,
   the Maps dynamite module in the API 31/33 emulator images (GMS 2023) crashes with
   `NoClassDefFoundError: org/apache/http/ProtocolVersion`. It is optional, so real devices are
   unaffected. For emulator smoke tests prefer `google_apis_playstore` images.
9. **Release artifacts** (`app/release/app-release.aab`) and `local.properties` are gitignored;
   do not add them back to version control. Build outputs (`**/build/`) and `.kotlin/` are
   gitignored too; a baseline profile generation used to commit `baselineprofile/build/` by
   accident and that history was rewritten, so never force-add those paths.
10. **`Theme.NoDisplay` crashes headless activities that suspend.** An invisible activity must
    call `finish()` before `onResume()` completes (targetSdk > 22); `NavigateActivity` waits for a
    Room query, so it always finished too late and crashed every time a shortcut was tapped.
    Verified on an API 37 emulator and reproduced in `NavigateActivityTest`. Use
    `Theme.AutoSpot.Translucent` (transparent window, `windowNoDisplay=false`) instead.
11. **An app update kills the monitor.** The process dies and the foreground service does not come
    back by itself, so auto-save used to stop silently until the app was opened.
    `BootReceiver` also listens for `MY_PACKAGE_REPLACED`; verified on the emulator by reinstalling
    the debug APK while the app was closed.
12. **Approximate location is not a usable permission.** If the user picks "Approximate" (Android
    12+), `hasLocation` is false, the monitor does not start and the manual save cannot work. The
    banner now says "Precise location required" instead of the generic permissions notice.
13. **A `startForegroundService` start must reach `startForeground`, even if the service stops.**
    Both services used to check their permissions first and call `stopSelf()` when they were gone.
    Android 12+ then killed the process with
    `ForegroundServiceDidNotStartInTimeException: startForegroundService() did not then call
    Service.startForeground()`. `BluetoothMonitorService` and `LocationSaveService` now enter the
    foreground before checking permissions and stop afterwards; the monitor fix was verified on an
    API 37 emulator by revoking background location and starting the service as the app UID.
    Covered by the `BluetoothMonitorServiceTest` and `LocationSaveServiceTest` permission tests.
14. **The monitor and the save service use different foreground-service types.** The monitor is
    `connectedDevice` (it only watches Bluetooth); `LocationSaveService` is `location`. The save
    service is started from the background while the monitor is running, which Android 14+
    restricts, so this exact combination was verified on a Pixel 7 Pro (Android 16): app in the
    background, paired A2DP speaker disconnected, `LocationSaveService` started and the location
    was saved. Re-run that test before changing either type or merging the services.

## Working rules for agents

- Do not `git commit`, `git push`, or open PRs unless explicitly asked.
- Never print, copy, or commit `local.properties` (Maps key), `keystore.properties`, or the release
  keystore.
- Keep changes consistent with the existing style: direct Compose + repository, and no new
  frameworks. Leave the `com.dicren.autospot` package as-is; it is the published `applicationId`.
- When architecture, commands, or conventions change, update this file in the same change.
